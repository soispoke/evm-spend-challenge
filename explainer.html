EVM Spend Challenge

Each private transfer in a privacy pool comes with a zero-knowledge proof that the spend follows the pool's rules. Today the minimal shielded pool writes those rules as a Circom circuit. Under EIP-8288 they could be written as a program and proved by a zkVM. This challenge measures how much that proof costs when the program is EVM bytecode run by an interpreter, compared with the same program compiled directly to RISC-V.

Entrants submit the EVM bytecode. The score is the number of RISC-V cycles it takes on a fixed version of leanVM. The result informs EIP-8288: if the EVM version costs close to the RISC-V version, applications could keep writing these programs in EVM bytecode, which weakens the performance case for letting them use RISC-V directly.

What we found

  • Plain Solidity takes 2.66 times the RISC-V cycles. Most of the extra is code the compiler generates around each hash call.
  • Hand-optimized entries take 1.36 times (Yul) and 1.34 times (hand-written bytecode). A program that only makes the 55 hash calls, with none of the checks, takes 1.22 times, so entries have little room left.
  • What remains is the interpreter. The same bytecode takes 1.10 times the RISC-V cycles when run by an interpreter written for proving, and 1.00 times when compiled ahead of time, so almost all of the gap comes from interpreting the program, not from EVM bytecode itself.
  • The interpreter matters more as hashing gets faster. At 200 cycles per SHA-256 compression, the hand-written entry would take 5.56 times the RISC-V cycles under REVM, 2.30 times with the new interpreter and 1.03 times compiled.
  • Gas ranks the entries in the same order as cycles but overstates their differences. The SHA-256 precompile costs about 85 cycles per unit of gas to prove, while the rest of the hand-written entry costs about 18 under REVM.

On the transfer case, the Solidity baseline executes 8,684 EVM instructions, mostly code the compiler generates around each hash: moving values on the stack, computing and bounds-checking input offsets, and jumps. The Yul entry executes 1,348 and the hand-written entry 1,242. Both have no loops, never branch on private data, have each precompile call write its result where the next hash reads it, and skip checking each call's result, because under the fixed gas limit a SHA-256 call cannot fail. The hand-written entry also keeps its working values on the stack and writes each tag byte and shared field once.

Gas follows the same order but overstates the differences: the Solidity baseline uses 2.82 times the gas of the hand-written entry and 1.99 times its cycles. The precompile's own 5,256 gas pays for 447,399 cycles of hashing, so in proving terms gas prices hashing about five times below the other work under REVM, and further below it with a faster interpreter.

How much is the interpreter

The score fixes REVM so that entries compete on their bytecode. To see how much of the remaining gap is the interpreter, the same bytecode also ran in three other ways. Each gives the same results and gas as REVM on every test case, and the two interpreters also on three million random programs.

  • REVM with a direct SHA-256 call: the precompile runs inside the call instruction, hashing EVM memory in place, instead of through a new call frame.
  • An interpreter written for proving: one dispatch loop, SHA-256 hashed straight from EVM memory, and gas checked only where a program can observe it.
  • Compiled ahead of time: each program translated into one Rust function, which shows about the best an interpreter could reach. A verifier would have to trust the compiler, or a proof that the compiled program matches the bytecode.

Proof times are medians of six leanVM proofs of one spend, from one interleaved run on an Apple M5 Max on AC power, without zero knowledge. Programs with the same padded trace took 0.81 to 0.88 seconds, so smaller differences are noise.

Proof time follows the padded trace, which leanVM rounds up to powers of two, table by table. The compiled version runs as many cycles as the reference, but its largest table ends just over a power of two that the reference stays 0.5% under, so its trace is 42% larger. The Solidity baseline gains the most from a better interpreter, from 2.66 to 1.94 times the RISC-V cycles, and 1.32 times compiled.

How the gap can change

Entries cut the EVM bytecode they run; the interpreter sets what each instruction costs. A zkVM accelerator for SHA-256 would cut the hashing cycles of both versions by the same amount, which lowers both totals but raises the ratio.

What the program checks

The rules are those of the minimal shielded pool's current spend: two input notes in a 20-level Merkle tree, two output notes, a public amount and a fee. Each output note is an amount plus the inner value its recipient provides. This version uses SHA-256 instead of Poseidon, fixed-width byte fields instead of field elements, and a one-byte tag at the start of every hashed message.

The input is 1,680 bytes, and the program makes 55 SHA-256 calls, 40 of them for the two Merkle paths. For a valid input it returns the 32-byte SHA-256 digest of the public values: both nullifiers, both output commitments, the root, domain, public amount, fee, recipient and authorizer. For an input that breaks any of these rules, it must return nothing:

0The input is exactly 1,680 bytes.
1Each input note's leaf index is below 220.
2For each input note with nonzero value, the Merkle path from its commitment leads to the root.
3The two input values do not sum to zero.
4The input values sum to the output values plus the public amount plus the fee, computed without wraparound.
5An output with value zero has inner equal to 1 if it is the first output and 2 if it is the second.
6An output with nonzero value has inner other than 1 and 2.
7The authorizer address is not zero.
8The recipient address is zero exactly when the public amount is zero.
9The two nullifiers differ.
10The two output commitments differ.

The specification gives the exact input layout and hash definitions.

Scoring

  1. The entry returns the expected digest for each of the 20 valid public test cases and returns nothing for each of the 39 invalid ones.
  2. It does the same on new test cases generated from fresh random seeds at scoring time.
  3. Every valid case is run on the fixed version of leanVM. The padded trace size must be the same for all valid inputs, because the proof reveals it.
  4. The score is the largest cycle count over the valid cases. Lower is better.

The invalid test cases cover every rule: removing any one rule check from any of the three entries makes a test fail. Entries are EVM bytecode, so other RISC-V zkVMs could prove both versions on the same machine to compare proof times, but the score comes only from the fixed leanVM version. Final timings should use zero knowledge, which Jolt supports and this leanVM version does not.

Beyond this challenge

Two questions matter for EIP-8288 that the score does not settle.

Changing the interpreter. The measurements above show that a better interpreter closes most of the gap. Swapping it changes no program, since programs are named by their bytecode, but it is a verifier upgrade: a proof shows that one specific interpreter build ran the program, so verifiers must trust that build to follow the EVM rules exactly. A second round could let entrants optimize the interpreter, with the tests against REVM as the correctness gate.

Stable meaning for immutable programs. A privacy pool's program must mean the same thing forever. The pool would name it by EVM version and bytecode hash, and the EVM used for proofs would change only by adding opcodes and precompiles in new versions, without gas metering. EVM implementations already keep every past fork's rules, so old versions stay cheap to support. The RISC-V base instruction set is already frozen.

Still to decide

What counts as close enough (proof time and peak memory with zero knowledge on a named laptop), how the hidden test seeds are chosen, whether other zkVMs count toward the score, and whether a second round targets the interpreter.
