EVM Spend Challenge

Under EIP-8288, a privacy pool could prove its spend rules with a zkVM proof of a program's execution. The program could be EVM bytecode, executed by an EVM interpreter inside the zkVM, or a RISC-V program compiled from Rust. We wrote the same spend check both ways and proved both with leanVM. How much more the EVM program costs to prove depends mostly on how its bytecode is executed, and on whether leanVM has an instruction for the hash precompile that the EVM program calls.

The spend check follows the minimal shielded pool's rules: two input notes in a 20-level Merkle tree, two output notes, a public amount and a fee. It makes 55 hash calls, 105 compressions of 64-byte blocks in total. The RISC-V program computes each hash either with base instructions, the standard RV64IM instructions that correspond to EVM opcodes, at about 3,100 cycles per BLAKE2s compression, or with leanVM's blake2s instruction, which computes one compression as a single instruction and so corresponds to an EVM precompile. The EVM program calls a hash precompile, which the interpreter computes with base instructions or with the blake2s instruction. Without a precompile, the EVM program computes the hash with EVM opcodes.

What this means for EIP-8288

EVM programs are practical when their heavy operations are precompiles that the zkVM computes with a dedicated instruction. Executed by the interpreter for proving, the EVM program then takes about twice the cycles of a RISC-V program using the same instruction, and nearly four times when executed by REVM.

One interpreter can execute every EVM program under one verification key. The interpreter takes the bytecode as input and hashes it, so each proof states that the program with this bytecode hash, run under a named fork's EVM rules, returned this output. Under the current EIP-8288 draft, a contract would accept the interpreter's verification key hash under the generic leanSTARK scheme, and an immutable contract would be stuck when that key changes. A dedicated scheme, whose fork configuration pins the interpreter and the verifier, lets contracts name their program by fork and bytecode hash instead. A faster interpreter or a new proof system then reaches every contract without changes. Because the program names its fork, a later fork that adds precompiles or reprices gas does not change what an existing program computes; the interpreter keeps every admitted fork's rules, as execution clients do. The interpreter becomes part of what verifiers trust: any deviation from the EVM rules could let a program accept an input it should reject, so it needs the same review and testing as a verifier.

The hash precompile has to match a zkVM instruction. L1 has the SHA-256 precompile at 0x02 and the KECCAK256 opcode. The leanVM version measured here has an instruction only for BLAKE2s, which has no L1 precompile; L1's BLAKE2 precompile at 0x09 computes the BLAKE2b compression, a different function. leanVM's README calls BLAKE2s a placeholder, with SHA-2, SHA-3 and BLAKE3 under consideration. If leanVM settles on BLAKE2s or BLAKE3, L1 needs a precompile for it, added by a hard fork before programs deploy, because a deployed program keeps the hash it was written with. If it settles on SHA-256 or SHA-3, L1 already has a match: the 0x02 precompile, or the KECCAK256 opcode, which uses the same Keccak permutation as SHA-3. A precompile also keeps the hash cheap on-chain, where a pool inserts commitments into its Merkle tree. Computed with EVM opcodes, BLAKE2s costs about 26,000 gas per compression.

Every other heavy primitive needs the same. A signature check inside a private account's program, for example, is practical only as an L1 precompile that the zkVM computes with a dedicated instruction. Computed with EVM opcodes, BLAKE2s takes 17 to 223 times the cycles of a RISC-V program computing it with base instructions, because opcodes on 256-bit words emulate its 32-bit arithmetic.

RISC-V remains the long-term target. RISC-V programs cost less to prove, and a new primitive can run on base instructions without a new precompile or a fork. Proving them directly under EIP-8288 needs one verification key for all RISC-V programs, with each program bound by its hash the way the interpreter binds bytecode. No RISC-V prover offers that yet. The interpreter is itself a RISC-V program, so EVM programs would keep working once one does.

The challenge

The challenge asks for the EVM bytecode that checks this spend in the fewest cycles, with the SHA-256 precompile at 0x02 as the only hash. Everything else is fixed: REVM executes the bytecode, and the leanVM version and SHA-256 code do not change. The score is the largest cycle count over the valid test cases, including new ones generated at scoring time. Three entries so far:

The two hand-optimized entries come close to a program that only makes the 55 precompile calls, at 1.22 times the RISC-V cycles, so the rest of the difference is the interpreter's cost. Gas ranks the entries in the same order but overstates their differences: the Solidity baseline uses 2.82 times the gas of the hand-written bytecode but only 1.99 times its cycles. The SHA-256 precompile's gas covers about 85 proving cycles per unit, against about 18 for the other opcodes under REVM.

The specification gives the rules, input format and scoring. The challenge has not launched.

How it was measured

The prover is leanVM's riscv-exploration branch at commit 1096dedf: RV64IM plus the blake2s instruction, without zero knowledge. Every program accepts all valid test cases and rejects all invalid ones on leanVM. The BLAKE2s precompile (at 0xb2 here) is hypothetical and priced like SHA-256. The interpreter for proving and the compiled programs are research code: they match REVM on every test case and on 3.6 million random programs, but they are not audited. Here each program's bytecode is built into the RISC-V program that leanVM proves; a production interpreter would take the bytecode as input and hash it, which for this program adds an estimated 10,000 cycles with the blake2s instruction.
