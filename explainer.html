EVM Spend Challenge

Under EIP-8288, a privacy pool could prove its spend rules with a program run in a zkVM. That program could be EVM bytecode run by an EVM interpreter, or RISC-V code compiled directly. We wrote the same spend check both ways and proved it with leanVM. How much more the EVM version costs depends mostly on how its bytecode is executed and on whether it can call the hash that the prover accelerates.

The spend follows the minimal shielded pool's rules: two input notes in a 20-level Merkle tree, two output notes, a public amount and a fee. Checking it takes 55 hash calls, 105 compressions. On RISC-V the hash is Rust code or leanVM's blake2s instruction. The EVM version calls a precompile, which the interpreter serves with the same code or instruction.

Results

  • With the hash accelerated on both sides, the interpreter sets the gap: 1.96 times the RISC-V cycles with an interpreter written for proving, 3.85 times with REVM, and 1.10 times with the bytecode compiled ahead of time.
  • With SHA-256 in software on both sides, the gap is only 1.10 to 1.34 times. Hashing takes 97% of the RISC-V cycles, and the EVM version runs the same hashing code.
  • An EVM program that cannot call the accelerated hash is about 10 times slower using SHA-256, and over 100 times slower with the hash written in EVM code.
  • A RISC-V program without the hash instruction takes 3.3 times the cycles of an EVM program whose precompile uses it.

Cycles are the largest count over all valid test cases and are exact for these builds. Proof times are medians of four to six proofs of one spend on an Apple M5 Max, without zero knowledge. The SHA-256 and BLAKE2s programs were timed in separate runs, and repeated runs varied by up to 40%. Proof time follows the padded trace, which leanVM rounds up to powers of two table by table, so equal cycle counts can prove at different speeds.

What this means for EIP-8288

EVM programs are practical when their heavy operations are precompiles that the prover accelerates. An EVM program then takes about twice the cycles of a RISC-V program using the same instruction when run by an interpreter written for proving, and nearly four times under REVM.

One interpreter can prove every EVM program. The interpreter reads the bytecode as input and hashes it, so each proof states that the program with this bytecode hash, run under a named fork's EVM rules, returned this output. Under the current EIP-8288 draft, a contract would accept the interpreter's verification key hash under the generic leanSTARK scheme, and an immutable contract would be stuck when that key changes. A dedicated scheme, whose fork configuration pins the interpreter and the verifier, lets contracts name their program by fork and bytecode hash instead. A faster interpreter or a new proof system then reaches every contract without changes. The interpreter becomes part of what verifiers trust: any deviation from the EVM rules could let a program accept an input it should reject, so it needs the same review and testing as a verifier.

The hash has to match. L1 has SHA-256 (precompile 0x02) and Keccak-256 (the KECCAK256 opcode). The leanVM version measured here accelerates only BLAKE2s, which L1 lacks. L1's BLAKE2 precompile at 0x09 computes the BLAKE2b compression, a different function. leanVM's README calls BLAKE2s a placeholder, with SHA-2, SHA-3 and BLAKE3 under consideration. If leanVM settles on BLAKE2s or BLAKE3, L1 needs a precompile for it, added by a hard fork before programs deploy, because a deployed program keeps the hash it was written with. If it settles on SHA-256 or SHA-3, L1 already has a match: 0x02, or the KECCAK256 opcode, which uses the same Keccak permutation as SHA-3. A precompile also keeps the hash cheap on-chain, where a pool inserts commitments into its Merkle tree; written in EVM code, BLAKE2s costs about 26,000 gas per compression.

Every other heavy primitive needs the same. A signature check inside a private account's program, for example, is practical only as an L1 precompile that the prover accelerates. In EVM code, BLAKE2s takes 17 to 223 times the cycles of a RISC-V program computing it in software, because 256-bit EVM instructions emulate its 32-bit arithmetic.

RISC-V remains the long-term target. RISC-V programs are faster and can add new primitives in software, without a fork. Proving them directly under EIP-8288 needs one verification key for all of them, with each program bound by its hash the way the interpreter binds bytecode. No RISC-V prover offers that yet. The interpreter is itself a RISC-V program, so EVM programs would keep working once one does.

The challenge

The challenge asks for the fastest EVM bytecode for this spend, with SHA-256 at 0x02 as the only hash and everything else fixed: REVM, the leanVM version and the SHA-256 code. The score is the largest cycle count over the valid test cases, including new ones generated at scoring time. Three entries so far:

Plain Solidity pays for code the compiler generates around each hash call. The two hand-optimized entries come close to a program that only makes the 55 hash calls, at 1.22 times, so the rest of the gap is the interpreter's cost. Gas ranks the entries in the same order but overstates their differences. The Solidity baseline uses 2.82 times the gas of the hand-written entry but only 1.99 times its cycles, because the SHA-256 precompile's gas covers about 85 proving cycles per unit, against about 18 for the other instructions under REVM.

The specification gives the rules, input format and scoring. The challenge has not launched.

How it was measured

The prover is leanVM's riscv-exploration branch at commit 1096dedf: RV64IM plus one custom instruction for the BLAKE2s compression, without zero knowledge. Every program accepts all valid test cases and rejects all invalid ones on leanVM. The BLAKE2s precompile (at 0xb2 here) is hypothetical and priced like SHA-256. The interpreter written for proving and the compiled programs are research code: they match REVM on every test case and on 3.6 million random programs, but they are not audited. Each program's bytecode is built into its guest here; a production interpreter would take it as input and hash it, which for this program adds an estimated 10,000 cycles with the instruction.
