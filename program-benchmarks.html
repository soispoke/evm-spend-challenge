Benchmark · 4 October 2026 · one M5 Max laptop

What each proof route costs

Eight statements, from signatures to 1 KiB hashes, each proved on leanVM as a RISC-V program compiled from Rust and as EVM programs that an EVM guest program executes inside the proof, on one laptop.

Takeaways

0.99–1.04×
EVM code is expensive to prove, and only precompiles hide it. In hand-written BLAKE2s, an EVM opcode costs about 50 RISC-V cycles on average. When a precompile does the heavy work, running the same Rust code as the RISC-V program, the EVM program proves about as fast as the RISC-V one: 0.99 to 1.04 times for secp256k1, SHA-256 and Keccak, which L1 already serves, and for Falcon-512, BLAKE2s and Poseidon through new precompiles.
35× or no proof
New cryptography needs a new precompile on the EVM side. Without one, BLAKE2s takes 35 times as long to prove, and Falcon-512, a post-quantum signature, cannot be proved at all, because its witness exceeds leanVM's cap even when raised, while the RISC-V program proves it in half a second. Each new primitive would need its own precompile, and so an L1 fork.
13.7×* → 1.8×
Hand-written EVM bytecode helps app logic, not cryptography. Writing the EVM program by hand instead of compiling it from Solidity cuts the state proof from 13.7 to 1.8 times the RISC-V time, and the shielded transfer from 1.7 to 1.4 times. It can't remove the per-opcode cost: hand-written BLAKE2s still takes 74 times the RISC-V program's cycles, and Falcon-512 stays too large to prove.
0.51×
RISC-V's own shortcut, a custom instruction, helps less than you'd expect. leanVM's BLAKE2s instruction cuts the cycles 15 times but the proof time only 2 times, because proof time follows the size of the committed witness, which only shrinks from 222 to 221 words.

Conclusion. Wherever a precompile does the heavy work, EVM programs cost about as much to prove as RISC-V programs; statements with logic of their own around the precompiles cost 1.4 to 1.8 times as much when the bytecode is written by hand, and up to 13.7 times when it is compiled from Solidity. Where L1 has no precompile, the EVM route is tens of times slower or cannot prove at all, so each new primitive, such as a post-quantum signature, needs a new L1 precompile and a fork, while the RISC-V route proves it directly from Rust.

Each number is a proof time over the RISC-V program's for the same statement, the median of the ratio within each round, over three rounds (seven where they were noisy or a proof is under 0.2 s); a range spans the statements its paragraph names; cycles are executed RV64IM instructions. * A proof in the ratio used MAX_MU, leanVM's cap on the witness, raised from 228 to 231 words, beyond what its verifiers accept. Every proof ran in one session on the laptop's 65 W adapter, each after an idle rest, so that all of them start from the same rested state.

program_id = hash(isa_version + program), from a draft program scheme, not in EIP-8288. A small cost can still cross a power of two: in the measured case, the BLAKE2s edition of the shielded transfer, it pushed the largest trace table past 216 rows, and the proof time went from 0.081 to 0.116 s.

All measurements

Cycles: RV64IM instructions executed on the program's largest valid test case; for the EVM routes, by the guest program written for proving. Witness: committed witness words, rounded up to a power of two. Proof vs RISC-V: the median ratio, then its range over the rounds.

Caveats

  • No zero knowledge: this leanVM version does not implement it.
  • One laptop: absolute times drift between rounds (the secp256k1 RISC-V proof took 3.0 s in one round and 4.8 s in another), and proving without idle rests slowed them: in the session the day before, on a 90 W adapter with no rests, long proofs slowed more than short ones.
  • The new EVM precompiles (BLAKE2s, Poseidon, Falcon-512) are hypothetical: on L1, each would take a fork.
  • The RISC-V programs use untuned standard crates while the hand-written EVM bytecode is optimized by hand, which favors the EVM routes.
  • Research code: differential-tested and reviewed, not audited.
What each program checks
  • secp256k1 signature. ECDSA over secp256k1 through ecrecover; the precompile runs the same k256 code as the RISC-V program.
  • Shielded transfer. The two-input, two-output spend of the EVM spend challenge (SHA-256 edition): 55 SHA-256 calls through the 0x02 precompile, two depth-20 Merkle paths, nullifiers and value conservation.
  • Private L1 state proof. A hidden account holds at least a public WETH balance at a public state root, checked against real mainnet proofs: WETH's 9-node account proof and a 7 to 9 node storage proof.
  • Falcon-512 signature. Falcon round 3 over the NIST KAT vectors; every program decodes the standard public key and takes its NTT itself.
  • Hashes. SHA-256, Keccak-256, BLAKE2s and circomlib's Poseidon over BN254 of one 1,024-byte message; the digest is the output.
How it was measured
  • Routes. RISC-V program and RISC-V custom instruction: leanVM proves the Rust program compiled to RISC-V, on base instructions or with leanVM's blake2s instruction. EVM Solidity, Existing EVM precompile, No EVM precompile and New EVM precompile: leanVM proves an EVM guest program, a RISC-V program that executes the bytecode opcode by opcode. Two EVM guest programs were measured: REVM 43.0.0, the Rust EVM used by Reth, and the guest program written for proving, which the figures use. The latter comes from the EVM spend challenge and serves precompiles without a call frame; it matched REVM's results and gas on every test case and on 3,000,000 random programs, whose calls target ecrecover, SHA-256 and P256VERIFY and whose opcodes include CLZ.
  • Same relation, same test cases. The programs of a statement take the same input and return the same digest. Each accepted every valid test case and rejected every invalid one, and every proof verified and was rejected against a changed public input.
  • Differential tests. 400 bit flips and 52 synthetic tries for the state proof, 300 bit flips and 44 encoding mutations for Falcon, and 646 crafted inputs from an adversarial review: the hand-written EVM bytecode agreed with the RISC-V program on every one. So did Falcon's program with the new EVM precompile, on its 16 test cases, 300 bit flips, 44 encoding mutations and 138 crafted inputs and NIST vectors, 71 of them with messages over 1,024 bytes. The EVM Solidity programs differ only inside third-party code, on crafted inputs: ZKNOX's Falcon decoder (26 of the 44 mutations, and compressed signatures of 666 bytes or more) and Optimism's trie (a value in a branch node's value slot).
  • Shared code. The guest programs serve ecrecover, SHA-256 and KECCAK256 with the same Rust functions the RISC-V programs call (k256 0.13.4, sha2 0.10.9, alloy-primitives). Shared code is the cycles of a control that makes only the shared calls, minus those of a null control that only starts the guest program and parses the input; for secp256k1 the RISC-V program itself is that control. Both halt normally on the largest valid test case.
  • Hand-written EVM bytecode. One hand-optimized version per statement and precompile choice, a single attempt rather than a proven best. The shielded transfer's is the spend challenge's entry, tuned for cycles under REVM; the others were written opcode by opcode with a small assembler. Falcon's Solidity version, ZKNOX's, is itself largely inline assembly. The state proof bytecode makes the same canonical-encoding checks as the RISC-V program, and Falcon's was tested stage by stage against a Python reference.
  • New EVM precompiles. BLAKE2s (0xb2), Poseidon with three BN254 inputs (0xb3) and Falcon-512 verification (0xb5) exist only in this benchmark: both guest programs serve them with the RISC-V program's Rust, as they serve SHA-256 at 0x02. Poseidon's is called once per permutation. Falcon's runs verify_signature, the RISC-V program's checks without the statement digest, which the 93-byte EVM program computes with 0x02.
  • Hashes. Every hash program takes one 1,024-byte message and returns its 32-byte digest; each accepted the 8 valid messages and rejected the wrong lengths (0, 1,023 and 1,025 bytes). Poseidon is circomlib's over BN254 (t = 4, x5, 8 full and 56 partial rounds), chained over 34 big-endian elements of at most 31 bytes, and matches circomlibjs 0.1.7. With no EVM precompile, the hand-written bytecode keeps four 32-bit lanes per word (BLAKE2s) or adds up to four products before reducing (Poseidon).
  • Variants. All Falcon programs verify round 3, the variant of the NIST KAT vectors and ETHFALCON, and cap messages at 1,024 bytes; the RISC-V program uses fn-dsa's arithmetic with round 3 decoders and norm check. All state-proof programs accept only canonical encodings, so they agree on crafted roots too.
  • Proof runs. M5 Max laptop, 18 cores, 17 worker threads, 128 GiB, without zero knowledge. Every proof time comes from one session on the laptop's 65 W adapter with the Linux VM stopped: three interleaved rounds of every program, each in a fresh process timed on its second proof after a warmup, and each after an idle rest of 20 times the previous program's run time, from 30 s to 5 minutes, because five idle minutes had restored full speed where one minute had not. Round 1 ran while the battery still charged (81% to 100%) and the Claude app kept other processes busier, and several of its proofs were slower. Comparisons whose rounds differed by more than 15%, or with a proof under 0.2 s, got four more rounds in the same environment, for seven in all. Each ratio is the median over rounds of the ratio within a round, which cancels the drift both proofs of a round share (the secp256k1 RISC-V proof took 3.0 s in one round and 4.8 s in another); the ratios themselves moved by up to 1.5 times between rounds. The day before, on a 90 W adapter and without rests, the same programs' proofs of a second or more took 1.57 to 2.01 times as long as here and those under 0.2 s 1.05 to 1.24 times; BLAKE2s with no EVM precompile took 54.6× the RISC-V program's time there, against 35.4× here. Tooltips also give REVM's cycles.
  • Pins. leanVM 1096dedf (riscv-exploration); REVM 43.0.0, Osaka rules; solc 0.8.30; ETHFALCON 820da4b6; optimism 81138275; guest toolchain nightly-2026-09-17, riscv64im. Solidity settings: secp256k1 signature (solc 0.8.30, optimizer on, 200 runs, Prague); shielded transfer (solc 0.8.30, optimizer on, via IR, 200 runs, Cancun); private L1 state proof (solc 0.8.30, optimizer on, 200 runs, Prague); Falcon-512 signature (solc 0.8.30, optimizer on, 10,000 runs, Cancun).
