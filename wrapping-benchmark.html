Benchmark · 6 October 2026 · one M5 Max laptop

What wrapping a proof costs

Wrapping, from Exposing an ISA for post-quantum privacy (h/t Vitalik): when the prover changes, users keep proving with the old prover, then make a second proof in the new system showing that the old verifier accepts the first. How much does that second proof cost? We measured it two ways on leanVM: running an earlier version's verifier as an ordinary program of the current version, and checking a proof in leanVM's recursion machine, a circuit built to check its own proofs.

Takeaways

11–22×
As a program, the old verifier does not fit in one proof. leanVM 1096dedf's verifier, run in leanVM 7532d46, takes 75.3M to 139.1M cycles to check one proof of the four statements. Its witness, 2^31.47 to 2^32.47 words, is 11 to 22 times what one proof holds, and leanVM cannot split a run across proofs, so this wrap cannot be proved today.
6.5–12×
It costs more than checking a Groth16 proof. A Groth16 verifier written for the same machine (leanVM PR 499) takes 11.6M cycles and also misses one proof (2^28.88 words); the old leanVM verifier takes 6.5 to 12.0 times that. Even its part that only checks the proof, the WHIR opening, ring switching, sumchecks and hashing, takes 26.1M to 30.7M.
25.0M–83.4M
Most of the cost comes from the old program, not from how long it ran. Reading the old program and proof and evaluating the program's columns takes 25.0M to 83.4M cycles, and the Flock circuits, fixed by the version, 16.2M. Committing each program once in a key (leanVM PR 418) would replace most of the program's part with one opening, for proofs made after it.
0.13–0.15 s
In the recursion machine, wrapping is cheap. It takes 0.133 s to 0.149 s for any leaf (0.087 s to 0.096 s with a circuit sized for wrapping only) and adds 8% to 63% to the user's proving time. But it checks proofs of its own version only, and leaves the program and Flock checks to the final verifier.

So wrapping does not let later forks forget the old system; it changes what they keep. Wrapping cheaply means every later recursion machine keeps a circuit for each old verifier, and users wrap their own old proofs so that mempool nodes need no old verifier. The recursion machine itself can still change at a fork: wrap proofs are made fresh for each transaction, so wallets just wrap with the new one.

Cycles. Parsing is exact, from a build that stops after reading the old program (decoding it, building and checking its bytecode table, hashing it into the program digest) and deserializing the proof; the parts of the verification are grouped by function from a profile and are approximate. The two programs have 55,464 and 207,496-byte ELFs. The port changes 1096dedf's verifier only where it computes: field products on the new machine's extmul instructions, BLAKE2s on its blake2s instruction, one thread, the bit transpose by 64x64 word blocks and the WHIR configuration from a table checked against its derivation. Before the last two, the shielded transfer's wrap took 178,869,270 cycles, more than half in the bit-by-bit transpose.

Caveats

  • The recursion machine's wrap verifies proofs of its own version. Wrapping an older version there would need the older verifier's rows in the newer machine, and in its final verifier the older bytecode encoding and Flock matrices it settles.
  • The guest's verifier is ported rather than rewritten for proving. Precomputing the Flock circuits, which each version fixes, and hints of the kind PR 499 plans for its Groth16 guest would lower its count, but its proof-dependent core alone, the WHIR opening, ring switching, the bus, the sumchecks and their hashing, takes 26.1M to 30.7M cycles.
  • The tree's setup, building both circuits from the program and the leaf's shape, takes 0.032 s to 0.036 s once per program and shape and is not in the wrap's time.
  • No zero knowledge: this leanVM version does not implement it, for leaves or for recursion proofs.
  • One laptop in use during the session: absolute times carry its background load, which each round's ratio largely cancels.
  • Research code, not audited.
How it was measured
  • What is proved. The leaves are the program benchmark's RISC-V programs (the shielded transfer, secp256k1, the private L1 state proof and Falcon-512), each on its largest valid test case, built for leanVM's current guest SDK with the same statement code, and leanVM's own Fibonacci program at four sizes. Their cycles are within 141 of the program benchmark page's. The wrap is a first-level node of leanVM's aggregation tree over one leaf: a recursion-machine proof that the RISC-V verifier's core accepts the leaf proof, with the claims on the program's bytecode, RAM image and Flock matrices left for the root's verifier, which settles them natively.
  • The cross-version wrap. The benchmark builds 1096dedf's verifier with std for rv64im, on std's zkvm platform layer (one thread, compare-and-swap lowered to calls the guest provides), against the current SDK. Its advice holds the old program's ELF, the old statement and the old proof as the old prover serializes it, and it commits the old program's digest, input and output. The old proofs are made with 1096dedf at rate 1, whose cycles match the program benchmark page's. The runs are counted with measure_unbounded (local patch), which runs past the cap that measure and proving refuse, as PR 499's Program::count does; every run gives the expected output, so the old verifier accepted each proof.
  • Pins. leanVM riscv-exploration at 7532d46 (6 October 2026), log inverse rate 1, the tree's nodes of two children; the wrap-only circuit is Tree::new_first_only from a local patch, which adds a constructor and changes nothing else.
  • Timing. One session on the laptop's 65 W adapter with the battery full, 3 rounds in rotated orders, every program in a fresh process after an idle rest of 20 times the previous process's proving time (30 s to 5 min). Each process proves the leaf twice and the wrap twice, timing the second of each, with 5 s before every proof. The machine was in use: the wait for other processes to fall below 25% CPU was capped at one minute, and each run's load is recorded beside it. Ratios are medians of the ratios within a round.
  • Refusals. Every run checks that the wrap's prover refuses a leaf whose output is changed and leaf proofs with one byte flipped at eight places, and that the wrap's verifier refuses other leaf outputs and wrap proofs with one byte flipped at eight places: all were refused. The prover's refusals come from the native verifier it runs first; that the rows themselves reject a forged transcript is leanVM's own test suite (rec/tree/tests.rs).
